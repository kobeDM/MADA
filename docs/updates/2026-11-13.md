# soft 停止と force 停止の保護 (2026-11-13)

仕様: [docs/specs/2026-11-12_2.md](../specs/2026-11-12_2.md) 4.3、5.4。API: [docs/specs/2026-11-12.md](../specs/2026-11-12.md) 4.4、4.4b。

- `POST /daq/stop/soft` を追加。`run/mada_stop_request.json` を書き、`mada.py` が各ファイルの終了後に確認して通常の終了処理に進む
  (`mada_file_cycle.run_period`、`mada_run_state.soft_stop_requested`)。取得中のファイルは最後まで取る。
- `POST /daq/stop`(force)は、ファイルの準備中/終了処理中は 409 `busy_file_update` で拒否する(ADALM制御中のSIGTERMを避ける)。
- `/status` の `daq.stop_mode`(`soft`/`force`)を追加。
- `mada.py` は起動時に前回の停止要求を消す。シミュレータも soft 停止に対応。
- 試験: `client/tests/test_client.py` に `test_soft_stop`、`test_force_stop_refused_between_files` を追加(13 passed)。
- 未確認: 実機での soft 停止(特にスケーラー動作中の period 途中終了)。

## スケーラーが file 0 を記録しなかった件 (20261104 per0029)

- 症状: `the scaler did not record file 0 (0 lines ...)` でDAQが停止。`runScaler` は起動し出力ファイルも作られたが、行は0。
- 切り分け(DAQ停止中、ADALMを直接操作): ZYBOの `sw_read_enable`(gpiochip5)は DAQ enable を上げて0、下げて1。
  単体の `runScaler` はこの操作で file 0 から正しく記録した。リセットパルスとソフトウェアベトは影響しない。
- 最初の仮説(誤り): `runScaler` は read enable が高い状態で最初に見た回を読み飛ばすため、起動時に低いと file 0 が欠ける。
  実際は起動時に高かった。ただし防止策として、起動前に read enable が高いことを最大5 s待って確認し、高くならなければ `ScalerError` で止める(`mada_scaler._wait_read_enable`)。
- 原因(per0030-0032 で確認): `runScaler` は記録に成功していたが、ZYBOのNFS書き込みキャッシュのため、DAQ PCから行が見えるのが
  数秒から数十秒遅れた(per0031/0032 は停止時に反映)。起動からDAQ enable までの時間は無関係(1.2 s でも3 s でも記録される)。
  ZYBOで `sync` すると即座に見える。
- 対策: `verify_file` が行を確認できないとき、最初に一度 ZYBO で `sync` を実行してから待つ。
- 起動前の read enable の確認は、読み飛ばしによる欠落の防止として残す。
- 実DAQでの確認: 未(次回の測定で、全ファイルの行が揃うこと)。
