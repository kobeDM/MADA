# 読み出しの停止を検出する警告ログ (perNNNN/warnings.log)

## 背景
- `per0026` で、1 基板のファイルから、他の基板が記録しているイベントがまとまって抜けた(GBKB-34 で 0.35 秒、GBKB-35 で 3.7 秒)。LVリセット、放電、NIC のエラーなどの記録はなく、基板から PC へのデータの流れが一時的に詰まったことまでしか絞れなかった。原因(ネットワーク側か、PC 側の書き込みか)を、次に起きたときに特定できるようにする。

## 変更
- `MadaIwaki` (`source/MadaIwaki.cc`) が、停止を 1 行ずつ標準エラーに出す(時刻はエポック秒 `t=`)。
  - `WARNING t=… kind=recv_wait sec=… events=… mean_interval=…`: 基板から `sec` 秒間、何も来なかった(通常の間隔の 10 倍超かつ `-t` 超)。基板・ネットワーク側。
  - `WARNING t=… kind=write_slow sec=… events=…`: ディスクへの書き込みとフラッシュに `sec` 秒かかった。PC 側。
  - `INFO t=… kind=summary events=… warnings=… max_recv_wait=… max_write=…`: ファイルが完了したとき。
  - 閾値は `-t/--warn-sec`(既定 0.2 秒)。受信が 50 回に達する前と、トリガーレートが低くて間隔が長いのが普通のときは、recv_wait を出さない。1 ファイルあたり最大 1000 件。
- `mada.py` が、これらを基板名つきで period のログ `perNNNN/warnings.log` に集める(`RunLogger.warning`)。読み出しの再起動、DAQ を止めたエラーも同じログに残す。ログに書けなくても DAQ は止めない。
- 形式: タブ区切りで、エポック秒、ISO 時刻、ファイル番号、発生源(基板名または `DAQ`)、メッセージ。

## 解析での使い方
- 欠落の時刻(`.info` の start + イベントのクロックカウンタ 100 µs 単位)と、`t=` を突き合わせる。
  - `recv_wait` が欠落と重なる: 基板からデータが来なかった(基板・リンク側、TCP の再送など)。
  - `write_slow` が重なる: PC 側の書き込みが遅れて、受信バッファが詰まった。
  - どちらも無い: 警告の閾値(0.2 秒)未満か、別の原因。

## 検証 (偽の基板、基板・ADALM には触れない)
- 200 Hz の流れに 1.0 秒の停止: `recv_wait sec=1.005 events=300` が 1 件、概要の行。
- 10 Hz の流れ: 0.4 秒(通常間隔の約 4〜5 倍)と 1.5 秒の停止を、それぞれ検出。
- 出力先を FIFO にして読み側を 1 秒止める: `write_slow` が約 1.0 秒で 2 件。
- 2 基板(片方が 1 秒停止)の実際の `MadaIwaki` を `start_readers` で起動: 停止の警告が、基板名と正確な時刻つきで `warnings.log` に入る。
- 取得サイクル全体(偽のバイナリ)で、起動失敗の再起動と、取得中に落ちた場合の `ERROR` が `warnings.log` に入る。
- 未確認: 実機の基板での出力(基板が電源オフ)。

## 追記: LVリセットも同じログに記録
- LVリセット監視 (別プロセス) が、DAQ の実行中だけ、書き込み中の period の `warnings.log` に、発生源 `LV` で追記する。
  - `WARNING … kind=over_limit module=… lines=… last="<MPOD の行>"`: 過電流の検知(電流値つき)。
  - `WARNING … kind=lv_reset_start modules=… boards=…` / `kind=lv_reset_end duration=… resets=…`。
  - 基板ごとに `INFO … kind=ap_off board=…`(コマンドを出した時刻)、`kind=ap_on board=…`(成功した時刻)。失敗は `ap_off_failed`、`ap_on_failed attempt=…`、`ERROR … kind=ap_left_off`。AP が OFF でスキップした基板は `ap_off_skip`。
  - veto は `kind=veto_assert` / `veto_release`(`veto.log` と同じ時刻)。失敗は `WARNING` で `…_failed`。
- 仕組み: DAQ (`mada_file_cycle.py`) がファイルの開始ごとに、書き込み中の period のパスとファイル番号を `run/mada_run.json` に公開し、終了処理で消す。監視は、その DAQ のプロセスが `mada.py` として生きている間だけ、そこに追記する(DAQ が落ちて状態が残っても、無視する)。DAQ が動いていないときは、どの period にも書かない。
- 書式の共通化: 書き込みは `mada_warning_log.py` に集約(`MadaIwaki` の行と同じ `LEVEL t=… kind=… key=value`)。
- 検証 (偽の AP 操作と veto): 状態なしでは書かない/ある場合は over_limit → lv_reset_start → ap_off → veto_assert → ap_on → … → veto_release → lv_reset_end の順/AP on の失敗が attempt 1〜3 で残る/死んだ PID の状態は無視する/取得サイクルが各ファイルで公開し、終了処理で消す。
- 注意: 稼働中の LVリセット監視は、変更前のコードのままなので、新しい記録を出すには、監視を止めて起動し直す(`mada_regulator_autoreset.py --stop`。次に DAQ を始めると、自動で新しいコードで起動する)。
