# 再実行時のカウンタリセット不良・DAC値異常の切り分け

## 症状(ユーザー報告)
- FPGA(ボード)の電源を入れ直さずにDAQを再実行すると、最初のファイルだけカウンタリセットが効かない。
- DAC値が適切に反映されない(全ToTがヒット)状態が、ピリオドを通して続く。
- 4基板すべてで起こるが、毎回ではない。トリガーは不明。8/28以前から存在し、9/22までの変更でも改善していない。

## 仮説
- H1: 前回実行のFPGA内部状態が残る(停止後もDAC/Vth/biasのシャドウレジスタ、0xf0のストローブ値が残ることを確認済み)。
- H2: `AP on` 後のASIC整定前にDAC適用ストローブが送られる(間欠性と整合)。
- H3: ラッチアップ検出ON直後の過渡でASICが保護状態に入る。
- H4: カウンタリセット経路(ADALM D8-D11 → ボード)の不達または不受理。
- H5: ソフトウェア変更による退行(ユーザー情報により8/28以降の変更は主因ではない見込み)。

## 検証で使ったツール
- .mada の解析(トリガーカウンタの減少点=リセット、ヒットビット数/レコード、常時ヒットのch数)、レジスタのダンプ比較、`ReadCtrlMem` のアドレス範囲指定、`mada.py` の一時オプションは、検証後に取り除いた。

## 正常データの特徴(2026-10-03 per0014)
- 最初のファイルにトリガーカウンタの減少が1回(リセット)あり、ヒットは平均0.6〜0.8ch/レコード(GBKB-34のみ約10)。

## 過去データの遡及調査(20260507/0724/0813/0817/20261003)
- (訂正) 20261003 の per0018 以降の全ヒット(GBKB-34/35)と0ヒット(GBKB-32/33)は、設定(Vth 10190/9220、`No00_base` のDAC)だけでは説明できない。同じ設定で電源投入直後に取った試験(10/09 14:07、テストパルス入力中)では GBKB-34/35 は9〜12ch/recordで飽和していなかった。per0018 は直前(10:14:21)にもセットアップが走った再実行だった。
- 20260724 の per0035/0036/0066/0067 に「リセット不良」らしい最初のファイル(カウンタ値が大きいまま)がある。ただし1ファイル/periodの開発期の運用で、現行運用の症例とは言い切れない。
- 20260817 の per0088 と per0099 は、4基板すべての最初のファイルでリセットが効いていない(カウンタ値が大きいまま)。報告の症状と一致する有力な症例で、per0067/per0085 の GBKB-33 にも同様の例がある。`run/20260817_0099.log` などの実行ログと突き合わせる価値がある。
- 全ヒット(`stuck=128`)の例は 20260724 の per0002, per0010 などにある。設定との対応は未確認。
- 結論: 既存データだけでは現行の症状を確定できない。管理した条件での再現が必要。

## 実機での観測(2026-10-09、電源投入直後からの1回目)
- 電源投入直後のレジスタは全て0。1回目の実行後(停止直後)は、DAC128ch、Vth、biasのシャドウレジスタが残っている(基板あたり132バイトがP0と異なる)。
- 1回目の実行はテストパルス入力中かつ既定設定で行ったため、ヒット数・レートは評価に使えない。

## 次の手順
1. テストパルスを止め、生産用の設定(Vth/bias/DACファイル)で再現試験をする。
2. 実行→停止→再実行を繰り返し、各回の最初のファイルをツールで判定し、停止後のレジスタを保存する(間欠性の統計を取る)。
3. 悪い回と良い回で、停止後レジスタ、起動直後のログ、最初のファイルのカウンタ経過を比較する。
4. 切り分け実験(`AP on` 後の待ち時間延長、SetAllDACの二重実行、停止時にAPを落とさない、ダミーファイルを先に取る)を、1要素ずつ行う。
5. カウンタリセット線とDAQ enable線をロジアナ/オシロで観測する。

## 再現と切り分け実験(2026-10-09、テストパルス停止後、設定は20261003のMADA_config.json)
- 再実行を1回行うと per0018 と同じパターンが再現した: GBKB-34/35 は全ヒット(128ch/record)、GBKB-32/33 は0ヒット。
- per0018 / 0019 / 0020 のセットアップ時のFPGAレジスタ読み戻し(`config/DAClog`)は、正常に書き込めた場合と全バイト一致した。FPGAのシャドウレジスタまでは正しく、異常はその先(ASICへの適用以降)にある。
- 実験(いずれも再実行状態から。ヒット数/record は GBKB-32/33/34/35):
  | 条件 | 結果 |
  |------|------|
  | E0: AP on → すぐ SetAllDAC | 0.0 / 0.0 / 128 / 128 |
  | E1: AP on → 10秒待つ → SetAllDAC | 0.0 / 0.0 / 128 / 128 |
  | E2: E0の後に SetAllDAC を1回、さらに1回(計3回) | いずれも 0.0 / 0.0 / 128 / 128 |
- AP on 後の待ち時間(H2)と、DAC書き込みの繰り返しは、状態を変えなかった。
- 未確認: 電源投入直後(再実行でない)かつテストパルス無しでの同条件の測定。これが分かれば「再実行による状態」か「設定の効果」かを確定できる。

## 電源再投入後のA/B比較(2026-10-09 15:0x、テストパルス停止、設定は同一)
同じ設定(Vth 10190/9220、bias 8000、`No00_base` のDAC)で、最初のファイル先頭400イベントを比較した。

| 条件 | GBKB-32 | GBKB-33 | GBKB-34 | GBKB-35 |
|------|---------|---------|---------|---------|
| A: 電源投入直後の1回目 | 19.1 | 24.5 | 9.2 | 12.3 |
| B: 電源を入れ直さない2回目 | 0.0 | 0.0 | 128 | 128 |
(値はヒットch数/record。128は全ch常時ヒット、0.0はヒット無し)

- 実行後のレジスタ(0x00-0x8f, 0xf0-0xff)は A と B で全基板とも差分0バイト。B の開始時は、前回の DAC/Vth/bias と 0xf0=0x04 が残っている。
- 0x90-0xef と 0x100 以降に、状態を示すレジスタは見当たらない(0xf0以外は全て0)。
- 追加の切り分け(いずれも B 状態から。結果は全て 0.0 / 0.0 / 128 / 128):
  - AP on 後に10秒待つ、SetAllDAC を計3回送る
  - APを約70秒OFFにしてから再投入する
  - Vth を +50 に書き換えてから目的値に戻す
- 結論: 異常な状態は、電源の入れ直し(FPGA)でのみ消える。AP の断続、DAC/Vth の再書き込み、待ち時間では回復しない。RBCPで読めるレジスタには現れない(FPGA内部状態、またはASIC側と推定)。
- ファームウェアの読み出し範囲では、Vth用DAC書き込み(`DAC_set.vhd`)はレベル駆動で、変更検出は無い。適用フラグ(`RBCP_REG.vhd` の vth/DAC/bias flag)は適用モジュールが消費するまで保持される。
- ボードのファームウェアは書き換えない方針(ユーザー指定)。

## 今後の候補
1. 回復手段の探索: SiTCP/RBCP側のリセット、適用フラグを消費させる別手順、FPGA再構成(電源以外の手段)が可能か調べる。
2. 予防: 異常の兆候(最初のファイルの全ヒット/0ヒット)を `mada.py` で自動検出し、DAQを止めて通知する。
3. カウンタリセットの1イベントずれ: トリガーのunixtimeとの突き合わせ解析を追加する。

## 原因の特定: ラッチアップ検出を有効にした実行が、次の実行を異常にする
- 配線の訂正(ADALMのGND接続をTI/TOからGNDへ)後も、再実行の異常は変わらなかった。W0/W1は未接続で、アナログ出力は原因ではない(`mada.py` からアナログ出力を外しても、2回目は異常だった)。
- DAQ enable を下げてからAPをOFFにしても、2回目以降は異常だった。停止手順の順序も原因ではない。
- 決め手(1回の電源投入内で連続実行、ヒット数/record は GBKB-32/33/34/35):
  | 実行 | 結果 |
  |------|------|
  | R1 検出なし | 18.4 / 23.5 / 8.7 / 11.8 |
  | R2 検出なし | 18.5 / 23.8 / 8.6 / 11.6 |
  | R3 検出あり(停止はAP OFFのみ) | 19.2 / 24.6 / 9.1 / 12.2 |
  | R4 検出なし(R3の次) | 0.0 / 0.0 / 127.5 / 127.5 (異常) |
  検出を有効にした実行そのものが、電源を入れ直すまで残る異常状態を作る。検出OFFの送信が原因ではない。
- ファームウェア(`LURecover.vhd`)は、検出有効時に全chヒットが一定時間続くとラッチアップと判定し、APのOFF/ON とDAC再書き込みを自律的に行う。その内部状態(`lu_judge`、各カウンタ)はRBCPのレジスタに出ず、FPGA電源の入れ直しでのみ初期化される。実際にどこで判定が起きて異常状態になるかは未確認。
- 対策の検証: `mada.py --no-latchup-detect` を電源を入れ直さずに3回続けて実行した結果、3回とも正常(1回目 18.4/23.9/9.1/12.2、2回目 18.5/23.8/8.6/11.6、3回目 18.7/24.0/8.5/11.5)。カウンタリセットも各回で効いている(トリガーカウンタの減少が1回)。
- 運用上の注意: 検出なしでは、基板内蔵のラッチアップ保護が働かない。外部のMPOD電流監視とLVリセット(`RegulatorAutoresetMonitor`)で保護する運用が前提。
- 未解決: 検出を有効にしたまま再実行の異常を避ける方法(検出を有効にするタイミングや、ファームウェアパラメータとの関係)。ファームウェアの書き換えはしない方針。

## 対応(2026-10-09)
- ラッチアップ検出はコンフィグで切り替える: `MADA_config.json` の `general.latch_up_detect`(1で有効、既定0)。`mada_encoder_power.py`(`mada.py` の起動・停止処理と単体CLIの両方)が参照する。
- 運用方針: ラッチアップ検出はうまく働かない場合も多いため使用しない(0)。
- 既存の運用ディレクトリの `MADA_config.json` に `general.latch_up_detect` が無い場合は、検出は無効として扱う。
