# daq-server 結合確認と修正の要望 (2026-11-12)

対象: `dev-cn1-daq-server` の aadd6e6(`server/`)。
確認方法: daq-client の模擬DAQ(`python3 client/mada_client.py --simulate`)にサーバーをつないで操作した。
API契約は [docs/specs/2026-11-12.md](../specs/2026-11-12.md)、サーバー仕様は [docs/specs/2026-11-12_3.md](../specs/2026-11-12_3.md)。

## 1. 確認できたこと(修正不要)

- ログイン(operator、viewer)。viewer の開始は 403、CSRFトークンなしの開始は 403。
- 開始、`running` 表示、ボード別の進捗、二重開始(`busy`)、停止、`last_exit: stopped`。
- ランの一覧、period のファイル一覧、履歴、ログの画面が 200 を返す。
- 通知: `period_done`、`daq_exit`(異常終了)、`connection_lost`、`connection_restored`。

## 2. 修正の要望

優先度: A=動作が仕様に反する、B=仕様の未実装、C=改善。

### 2.1 [A] ファイル0番の無効通知が出ない

- 場所: `server/mada_server_poller.py` の `_poll_files`(186行目)
  `after = self._files_max_id.get(target, 0)`
- 問題: 契約の `after` は「それより大きいファイル番号」(API契約 4.7)。既定が 0 だと、ファイル0番が毎回除外される。
- 再現: 模擬DAQを `--sim-invalid-file 0` で起動して開始すると、ファイル0番が無効で終わるが `file_invalid` 通知が出ない。
- 修正案: 既定値を `-1` にする(最初の問い合わせは `after=-1` でよい)。

### 2.2 [A] 経過時間がサーバーとクライアントの時計のずれの影響を受ける

- 場所: `server/static/app.js` 69行目
  `data.server_time - daq.started_at`
- 問題: `server_time` はサーバーの時計、`started_at` はクライアントの時計。時計がずれると経過時間が狂う
  (サーバー仕様 4 は「クライアントの時刻をそのまま使う」)。
- 修正案: `status.time`(`/status` の取得時のクライアント時刻)を使う。 `stop_requested_at` からの経過も同様。

### 2.3 [B] `stopping` が長引いたときの案内が未実装

- 仕様: サーバー仕様 3.2「`stopping` の間は経過時間を表示し、長引く(目安2分)ときは『後処理が長引いています。
  端末での確認が必要かもしれません』と示す」。
- 現状: `app.js` に `stop_requested_at` を使う箇所がない。
- 修正案: `status.daq.stop_requested_at` と `status.time` の差を表示し、120 s を超えたら警告を出す。

### 2.4 [B] サーバーを再起動すると通知が重複する

- 場所: `mada_server_poller.py` の `_notified_exit_time`(36行目)、 `_files_max_id`(41行目)、
  `_prev_period_by_run`(35行目)。いずれもメモリのみ。
- 問題: 再起動後の最初のポーリングで、すでに通知した `last_exit` と無効ファイルを再び通知する。警告の取得位置
  (`warnings_cursor`)だけはDBに保存されている。
- 修正案: 通知済みの `last_exit.time` と、ファイルの取得位置をDBに保存する。または、通知の重複を種類と内容(run、period、
  file_id、 `last_exit.time`)で抑える。

### 2.5 [C] 終了直前の警告がライブのフィードから漏れる

- 場所: `mada_server_poller.py` の `_on_status_success`(108行目付近)
- 問題: `phase` が `idle` になった時点で `_current_run_period` が `None` になり、その直前の最大5 s分の警告
  (DAQを止めた原因の記録など)を取得しないまま追従が止まる。period が替わるときも同様。
- 修正案: `idle` になった後、または period が替わった後に、もう1回だけ前の (run, period) の警告を取得してから切り替える。

### 2.6 [C] `period_done` の意味

- 場所: `mada_server_poller.py` の `_check_period`(130行目付近)
- 現状: period 番号が増えると通知する。DAQを停止して開始し直すと、新しいperiodの番号が前より大きいため、
  停止で終わった period にも「完了しました」と出る。
- 修正案: `daq.valid_files >= daq.file_num` の状態から period が替わった場合だけ「完了」とする。停止で終わった場合は別の文言にする。

## 3. 再現手順

```bash
# 模擬DAQ(1ファイル1秒、ファイル0番が無効、3ファイルで失敗)
python3 client/mada_client.py --simulate --sim-home /tmp/mada_sim --sim-file-sec 1 \
        --sim-invalid-file 0 --sim-fail-after 3 --port 18766
# トークンは sim-token。サーバー設定の client.base_url を http://127.0.0.1:18766、token_file を上記トークンに向ける
```

模擬DAQの他のオプションは `python3 client/mada_client.py --help` を参照する。クライアントは `dev-cn1-daq-client` ブランチにある。

## 4. 補足

- サーバー側にテストがない。ポーラーの通知判定(2.1、2.4、2.6)は、`DaqClient` を差し替えた単体テストにしやすい構造である。
- このブランチは `server/` 以外のDAQコードを外してあるため、`dev-cn1` や `dev-cn1-daq-client` とはマージしない前提と理解している。
  API契約に変更が必要になった場合は、両ブランチの `docs/specs/` を揃える。
