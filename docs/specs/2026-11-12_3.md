# DAQサーバー 仕様書 (`daq-server`)

別PCで動き、DAQ PC(クライアント)のAPIを呼んで、ブラウザからDAQを操作・監視できるようにするWebサーバー。
サーバーとクライアントの間の取り決めは [API契約](2026-11-12.md) を参照。クライアント側は [クライアント仕様書](2026-11-12_2.md)。
ブランチは `dev-cn1-daq-server`。

## 1. 目的と範囲

- ブラウザから、DAQの状態(phase、進捗、警告)を見て、開始と停止を行えるようにする。
- 初期版の対象はDAQのみ。管理するDAQは1台。スキャン、較正、config編集、複数DAQは後版。
- サーバーはDAQの動作に必須ではない。サーバーが落ちても、DAQもデータ取得も止まらない。
  サーバーはハードウェアに直接触れず、データ本体(`.mada`)も扱わない。

## 2. 全体構成

```
[ブラウザ] <--HTTP(S)--> [サーバー] --HTTP--> [クライアント(DAQ PC)]
                          |-- ポーラー(クライアントのAPIを周期取得、最新状態を保持)
                          |-- Web API / 画面(ブラウザ向け)
                          `-- DB(ユーザー、操作履歴、通知)
```

- ブラウザはクライアントに直接つながない。トークンはサーバーだけが持つ。
- ポーラーは、ブラウザの接続の有無に関わらず動き続け、最新の状態を保持する。ブラウザの要求のたびに
  クライアントを呼ばない(閲覧者が増えてもクライアントの負荷が変わらない)。
- ブラウザへの状態の配信は、SSE(Server-Sent Events)を推奨する。ポーリングでも可。

## 3. 機能要件

### 3.1 ダッシュボード
常時表示する。

| 項目 | 元になるAPI | 内容 |
|---|---|---|
| 接続状態 | `/status` の成否 | 接続中 / 接続断(最後に成功した時刻) |
| phase | `/status` | `idle`、 `starting`、 `running`、 `stopping`。色分け |
| 実行情報 | `/status` の `daq` | run、period、ファイル番号、 `valid_files` / `file_num`、 `event_num`、起動からの経過時間 |
| ボード別進捗 | `/progress` | ボードごとのイベント数 / `event_num` のバー。 `lagging` のボードを強調 |
| 保護機構 | `/status` の `monitor` | 自動リセットモニタの生存、vetoの状態。異常は目立たせる |
| 直近の終了 | `/status` の `last_exit` | `error` や `crashed` のときに理由を表示(確認済みにするまで残す) |

### 3.2 操作
- **開始**: `run`、 `file_num`、 `event_num`、 SCI の有無を入力する。
  - `run` は、既存のrunを選んで続ける(既定は `latest_run`)か、新しいrunの名前を入力する。新しいrunの名前は
    サーバーが規則に従って提案できる(例: 当日の `YYYYMMDD`。既存のrunと重なる場合は連番を付ける)。`GET /runs` で
    名前の重なりを確認する。
  - 新しいrunのときは、configのコピー元のrunを選べる(既定は `latest_run`)。開始前の確認画面に、出力先のrun、
    新規か継続か、コピー元を表示し、 `GET /runs/{run}/config` から有効なボード(`active`)とVth/biasの一覧も出す
    (読み取りのみ)。
  - 継続するrunと新しいrunを取り違えないよう、確認画面で明示する。
  - 線源ごとのプリセットを持てる(例: 55Fe 5000、252Cf 2000 events/file)。プリセットはサーバーの設定に置く。
  - `phase` が `idle` で `blocked_by` が無いときだけ押せる。
- **停止**: 確認ダイアログの後で `POST /daq/stop`。 `phase` が `running` のときだけ押せる。
  `stopping` の間は経過時間を表示し、長引く(目安2分)ときは「後処理が長引いています。端末での確認が必要かもしれません」と示す。
  強制終了のボタンは作らない。
- 操作の送信後はボタンを無効化し、`phase` が変わるか、タイムアウト(開始90 s、停止180 s)するまで待つ。
  タイムアウトしたら状態不明として表示する(失敗とは断定しない)。
- 受理(202)と完了を区別する。「開始しました」ではなく「開始を要求しました」と表示し、 `running` になって初めて開始とする。

### 3.3 履歴とログ
- ファイル一覧: period ごとに、ファイル番号、有効/無効(理由)、開始・終了、サイズを表にする。無効ファイルを目立たせる。
- 警告: `warnings` を時系列に表示。 `level`(`WARNING`、 `ERROR`、 `INFO`)と `source`(ボード、 `DAQ`、 `LV`)で絞り込める。
  `LV`(過電流リセット)と `board_lag` は件数を集計して表示する。
- デーモンログ: `/log` の追い読みで、末尾追従のテキストビューを持つ(開いている間のみ取得)。
- 過去のrun/periodの閲覧は `/runs` から辿る。

### 3.4 通知
次を検知したら、画面上の通知とDBの通知履歴に残す。外部への送信(メール、Slack等)は初期版では行わない。

| 事象 | 検知 |
|---|---|
| DAQが異常終了 | `running` / `starting` → `idle` で `last_exit.reason` が `error` / `crashed` |
| periodの完了 | `period` が増えた |
| 接続断 / 復旧 | `/status` の連続失敗 / 成功 |
| 保護機構の異常 | `monitor.autoreset_running` が false、 `veto.failed` が true |
| ファイルが無効 | `files` に `valid: false` が現れた |
| 進捗が止まった | `/progress` の `stale` が true |

### 3.5 認証と操作の記録
- ログインしたユーザーだけが画面を見られる。ロールは `viewer`(閲覧のみ)と `operator`(開始・停止も可)の2種。
- 開始・停止は、ユーザー、時刻、パラメータ、クライアントの応答(HTTPステータス、 `error.code`)を操作履歴に残す。
  履歴は消せない(追記のみ)。
- 同時に複数人が操作できるが、実際に通るのは先着の1件(クライアントが排他する)。後の人には 409 の理由を表示する。

## 4. ポーリング

[API契約](2026-11-12.md) 6 の周期に従う。

- `/status`: 2 s、 `/progress`: 1 s(`running` のみ)、 `warnings`: 5 s、 `files`: 10 s。
- 連続3回(約6 s)失敗したら「接続断」とする。接続断の間、phaseは「不明」と表示し、 `idle` と見せない。
  復旧するまで、指数バックオフ(2 s → 最大30 s)で `/status` のみ再試行する。
- クライアントの時刻をそのまま使う。サーバーとクライアントの時計がずれていても、表示の整合が取れる。
- ブラウザが0人でも、ポーラーは `/status` と `warnings` を取り続け、通知と履歴を取りこぼさない。
- `warnings` の取得位置(最新の `t`)は永続化し、サーバーの再起動で重複や欠落を起こさない。

## 5. データ

| 保存するもの | 場所 | 内容 |
|---|---|---|
| ユーザー | DB | ID、パスワードのハッシュ、ロール |
| 操作履歴 | DB | 追記のみ(3.5) |
| 通知履歴 | DB | 3.4、確認済みの印 |
| 警告の取得位置 | DB | 3.4 の取りこぼし防止 |
| 最新の状態 | メモリ | `/status`、 `/progress` の最新値(再起動で消えてよい) |

ファイル一覧と警告の本体はクライアントのディスクが原本。サーバーは必要なものだけをキャッシュし、原本を複製しない。

## 6. セキュリティ

- サーバーの設定に、クライアントのURLとトークンを持つ。トークンはファイル(パーミッション 600)か環境変数で与え、
  設定JSONやリポジトリに書かない。ブラウザや画面、ログに出さない。
- 画面は研究室内のネットワークで公開する前提とする。外部に出す場合は、HTTPS(リバースプロキシ)と、より強い認証を追加する。
- ブラウザからの操作系の要求(開始・停止)には、CSRF対策を入れる。
- 入力は、サーバー側でも検証する(API契約の範囲)。クライアントの検証を当てにしない。
- パスワードはハッシュ(bcrypt等)で保存する。

## 7. 実装方針

- 言語とフレームワークは、クライアントと同じPython/FastAPI を推奨する(API契約のスキーマをpydanticのモデルとして共有でき、
  どちらかの変更が型の不一致として早期に分かるため)。画面は、サーバーが返すHTML+少量のJavaScript(htmx等)から始め、
  必要なら分離する。最終的な選定は未決事項。
- クライアントへの呼び出しは、1つのクライアントクラスに集約する(タイムアウト 5 s、ベースURLとトークンを持つ)。
  画面や通知のロジックはそのクラスだけを通して通信する。
- 開発と試験には、クライアントのシミュレータ(クライアント仕様 4.7)を使う。実機がなくても、正常、異常終了、
  `board_lag`、接続断を再現できる。
- サービス化(systemd)と再起動耐性: 再起動後に、DBの取得位置から再開する。

## 8. 実装の順序

1. クライアントクラスと、シミュレータ相手の読み取り(状態、進捗、警告、ファイル)。
2. ポーラーと最新状態の保持、接続断の扱い。
3. ダッシュボード(3.1)と履歴・ログ(3.3)。
4. 認証、ロール、操作(開始・停止)と操作履歴(3.2、3.5)。
5. 通知(3.4)。
6. 実機のクライアントとの結合試験: 開始・停止、異常終了、接続断、サーバー/クライアントの再起動。
