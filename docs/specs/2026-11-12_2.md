# DAQクライアント 仕様書 (`daq-client`)

DAQ PC上で動き、既存のMADAをHTTP APIで外部から操作・監視できるようにする常駐プログラム。
API自体の定義は [API契約](2026-11-12.md) を参照。ここでは、クライアントの内部動作とMADA本体への変更を定める。
ブランチは `dev-cn1-daq-client`。

## 1. 方針

- 既存のDAQ(`mada.py` 以下)の動作は変えない。クライアントはその外側に被せる薄い層とする。
- クライアントは、`mada.py -d` を起動し、SIGTERMで止め、MADAが書くファイルを読んで返すだけである。
  ハードウェア(ボード、ADALM、電源)には直接触れない。
- クライアントが落ちてもDAQは止まらない。クライアントを再起動すれば、ファイルとプロセスから状態を復元できる。
  クライアント自身の状態は最小限にする。
- 公開する操作は、DAQの開始と安全な停止のみ。任意コマンドの実行、強制終了(SIGKILL)、configの書き換えは提供しない。

## 2. 構成

```
client/
  mada_client.py           起動(引数、設定読み込み、uvicorn起動)
  mada_client_app.py       FastAPIアプリ、エンドポイント、認証、エラー変換
  mada_client_ops.py       DAQの開始・停止、排他
  mada_client_state.py     phase の導出、status/progress の組み立て
  mada_client_files.py     run/period/file/警告/ログの読み取り
  mada_client_config.py    クライアント設定の読み込みと検証
  mada_client_simulator.py シミュレータ(4.7)
config/
  MADA_client_SKEL.json    クライアント設定の雛形
```

- `scripts/` のモジュール(`mada_config`, `mada_run_state`, `mada_process`, `mada_warning_log` など)は、
  `$MADAHOME/scripts` を `sys.path` に加えてimportして再利用する。同じ処理を二重に実装しない。
- 実装言語はPython 3。フレームワークは FastAPI + uvicorn(`pip install fastapi uvicorn`)。入力検証と
  OpenAPIの自動生成が得られるため。`psutil` は既存の依存。

## 3. クライアント設定 (`config/MADA_client.json`)

```json
{
    "listen_host": "0.0.0.0",
    "port": 8765,
    "allowed_servers": ["192.168.0.10"],
    "token_file": "/home/msgc/.mada_client_token",
    "data_root": "/nadb61/cn_tc/data",
    "carry_over_config": true,
    "defaults": { "file_num": 512, "event_num": 1000 },
    "limits": { "file_num_max": 10000, "event_num_max": 100000 }
}
```

- `allowed_servers`: 接続を許可するサーバーのIP。これ以外は 403 `forbidden_origin`(`/health` を含む全体)。
- `token_file`: トークン(1行)を置いたファイル。パーミッションは 600 でなければ起動しない。トークンは設定JSONやリポジトリに書かない。
- `data_root`: runディレクトリ(出力先)の親。 `run` はこの直下の名前に限る(形式は API契約 4.3)。実体パスが
  `data_root` 配下であることも確認する。
- `carry_over_config`: 新しいrunで `config_from` が無いとき、 `MADA_config.json` を持つ直近のrun(`latest_run`)から
  configをコピーするか。false なら 422 `config_not_found`。
- DAQのconfigは、従来どおりrunディレクトリの `MADA_config.json` である(ボードのIP、Vth、DACファイル、ADALM等)。
- 設定の誤りは起動時に全件列挙して終了する(MADA本体の `ConfigError` と同じ流儀)。

### 3.1 runディレクトリの管理
- run は区切りの単位で、日付とは限らない。何日にもわたって続くこともあれば、1日に複数作ることもある。
  クライアントは名前を自動では決めず、サーバーが `run` で指定する。
- 作成: 指定された `data_root/<run>` が無ければ新しいrunとして作る。ある場合は再利用し、続けて取得する
  (`perNNNN` の番号は `RunLogger.new_period()` が空き番号から続けるので衝突しない)。
- 動作中: DAQは起動したrunのディレクトリに書き続ける。runは動作中に変わらない。runを替えるには停止して開始し直す。
- 中身: `perNNNN/`、 `calibNNNN/`(較正)、 `MADA_config.json`、必要ならスキャンの出力。クライアントは `perNNNN/` の
  外側を読まず、削除・移動・名前変更をしない。
- configの引き継ぎ: 新しいrun(または `MADA_config.json` が無いrun)だけに行う。コピーのみで内容は編集しない。
  コピーしたこと(コピー元のrun名)は `$MADAHOME/run/mada_client.log` に残す。コピー後のconfigはそのrunの独立した
  ファイルで、その後の変更は元のrunに影響しない。既に `MADA_config.json` があるrunは上書きしない。
- 一覧: `GET /runs` は、 `data_root` 直下で `perNNNN` を持つディレクトリを返す。 `data_root` の他の内容は見せない。
- ログ: デーモンのログは `$MADAHOME/run/<run>_<period>.log` で、run名が違えば衝突しない。

## 4. 動作

### 4.1 phase の導出
クライアントは `phase` を内部に保持せず、毎回ファイルとプロセスから導く。

1. デーモンのPID: `$MADAHOME/run/mada_daemon.pid` が生きていればそれ。無ければ `read_run_state()` のPID
   (端末から手動で起動された `mada.py`)。
2. PIDが無ければ `idle`。
3. 停止要求済み(クライアントが記録した `stop_requested_at` がこのPIDに対して有り)なら `stopping`。
4. `read_run_state()` がこのPIDのものを返せば `running`、返さなければ `starting`。

`idle` のとき、`mada_scan.py`、`mada_calib.py`、`MadaIwaki` が動いていれば `blocked_by` に入れる(`find_processes` を使用)。
`last_exit` は `$MADAHOME/run/mada_last_exit.json`。ただし、記録の `time` が直近の起動より古ければ(今回の終了ではない)
`crashed` を返す。

### 4.2 開始 (`POST /daq/start`)
1. 認証と入力検証(`run` の形式、範囲)。
2. 開始処理は排他ロックの下で直列に行う。 `phase` が `idle` でなければ、または `blocked_by` があれば 409。
3. runディレクトリ `data_root/<run>` を作成(無ければ)。 `MADA_config.json` が無ければ、 `config_from` のrun、
   なければ(`carry_over_config` が true のとき) `latest_run` からコピーする(3.1)。コピー元が無ければ 422 `config_not_found`。
   `MADA_config.json` があるrunに `config_from` が指定されていれば 422 `invalid_request`。
4. サブプロセスで `mada.py -d -c MADA_config.json -f <file_num> -n <event_num> [--sci]` を実行する。
   - `cwd = data_root/<run名>`、環境変数 `MADAHOME` を設定。引数は固定の組み立てのみで、シェルを介さない。
   - `mada.py` は設定検査に失敗すると、デーモン化の前に非ゼロで終了する。その出力を 422 `config_invalid` の `message` に入れる。
   - 成功すると親は PID ファイルを書いて直ちに終了する。終了コード0を確認したら 202 を返す。
   - 親プロセスが 30 s 以内に終了しなければ、サブプロセスを終了して 503 `start_failed`。
5. 起動パラメータ(run、file_num、event_num、sci、起動時刻)を `$MADAHOME/run/mada_client.json` に記録する
   (`starting` の間の `daq` の内容と、起動後の `started_at` に使う)。

電源投入以降の失敗(ボード無応答など)はデーモン化後に起こるため、開始APIでは分からない。
サーバーは `phase` が `starting` → `idle` に戻ったときに `last_exit` を確認する。

### 4.3 停止 (`POST /daq/stop`)
- 4.1 のPIDに SIGTERM を送り、 `stop_requested_at` を記録する。 `mada.py` は SIGTERM を Ctrl+C と同じ後処理に
  つなぐ(`install_sigterm_handler`)ため、電源OFFまで行われる。
- 後処理には数十秒かかりうる。クライアントは待たずに 202 を返し、プロセスの消滅で `idle` に戻る。
- soft 停止(`POST /daq/stop/soft`): 停止要求を `run/mada_stop_request.json` に書き、 `stop_mode: "soft"` を記録して
  `stopping` にする。 `mada.py` は各ファイルの終了後(`run_file` が戻った直後、次のファイルの準備に入る前)にこの要求を確認し、
  あれば通常の終了処理に進む(Ctrl+C と同じ後処理)。取得中のファイルは最後まで取る。 `starting` の間は force 停止と同じ扱い。
- force 停止は、 `file_started_at` が null の間(ファイルの準備中)と、進捗ファイルが無い間(ファイルの終了処理中)は
  409 `busy_file_update` で拒否する。 `mada.py` が ADALM を制御している間に SIGTERM を送ると、DAQ enable が上がったまま、
  またはカウンタリセットが中途半端な状態で止まりうるため。soft 停止中の force 停止も同じ条件で受け付ける。
- SIGKILL への自動エスカレーションはしない。 `stopping` が長引く場合は、サーバー側で表示して人が判断する
  (`daq.stop_requested_at` から経過時間が分かる)。

### 4.4 読み取り系
- `status`: 4.1 の導出に、`run/veto.state`(`failed`、`asserted`)とモニタの生存(`mada_autoreset_ctl.monitor_pid()`)、スケーラーの状態(`run/mada_scaler.json`)を加える。
  スケーラーの起動・停止は `mada.py` が行い(クライアントはsshを呼ばない)、動作中と記録されているのにDAQが動いていなければ `orphaned` とする。
- `progress`: `run/mada_progress.json`(5.2)を返す。更新が5 s以上古い、またはPIDが違えば `stale: true`。
  soft 停止の `stopping` の間も返す(取得中のファイルが終わるまで)。idle、starting、force の stopping は空。
- `files`: `perNNNN/*_NNNN.info` を読む。ボードごとの `.info` から `runinfo.valid`、 `invalid_reason`、 `start`、 `end`、 `size`
  をファイル番号ごとにまとめる。period 全体の再読み込みを避けるため、 `after` で範囲を絞り、 `.info` はmtimeでキャッシュする。
- `warnings`: `perNNNN/warnings.log` のタブ区切り(時刻[s]、ISO時刻、ファイル番号、source、メッセージ)を解析する。
  `LEVEL t=... kind=...` 形式の `level`、 `kind` を取り出す。追記中の最後の不完全な行は読み飛ばす。
- `log`: `$MADAHOME/run/<run>_<period>.log` のバイト位置による追い読み。 `offset` が末尾を超えていれば先頭から。
  UTF-8の途中で切れた末尾は次回に回す。
- `config`: `data_root/<run>/MADA_config.json` を返すのみ。
- `latest_run`: `data_root` 直下で `perNNNN` を持つディレクトリのうち、更新時刻が最新のもの。

### 4.5 認証と通信
- すべての要求で、接続元IPが `allowed_servers` に含まれ、かつ `Authorization: Bearer` がトークンと一致すること
  (定数時間比較)。失敗は 403 / 401。
- 通信は平文のHTTP。研究室内のネットワークで、接続元IP制限とトークンで守る前提とする。
  外部ネットワークに出す場合はTLS(リバースプロキシ)を別途追加する。
- 操作系(start、stop)は、接続元IP、時刻、パラメータ、結果を `$MADAHOME/run/mada_client.log` に記録する。

### 4.6 サービス化
- DAQを動かすユーザーのsystemdユニットとして常駐させる(ADALMのUSB、 `MADAHOME`、ROOTの環境が必要なため同じユーザー)。
- 環境は `~/setup_claude.sh` と同等のものを、ユニットの `ExecStart` で読み込む。
- クライアントを再起動してもDAQは影響を受けない(`mada.py -d` は `setsid` した別プロセス)。

### 4.7 シミュレータ
サーバー側の開発と試験のため、実機なしでAPIを返せる模擬モードを持つ。

- `mada_client.py --simulate`: `MADAHOME` を一時ディレクトリに作り、`mada.py` の代わりに模擬デーモンを起動する。
- 模擬デーモンは、実機と同じファイル(`mada_daemon.pid`、 `mada_run.json`、 `mada_progress.json`、 `perNNNN/*.info`、
  `warnings.log`、 `mada_last_exit.json`)を、短い周期(1ファイル数秒)で作る。
- 正常終了、異常終了(`last_exit` が `error`)、`board_lag` 警告、 `stale` の進捗を再現するオプションを持つ。

## 5. MADA本体の変更(最小)

クライアントが必要とする機械可読な情報が、現状は端末出力にしか無い。次の3点を追加する。DAQの取得動作は変えない。

### 5.1 実行状態の拡張 (`run/mada_run.json`)
現状は `pid`、`period_dir`、`file_id` のみ。次を追加する(`publish_run_state` に引数を追加)。

| 追加フィールド | 内容 |
|---|---|
| `run` | 起動ディレクトリ名(`mada_daemon.run_name()`) |
| `period` | period 番号(整数) |
| `valid_files` | 現periodで有効に終わったファイル数 |
| `file_num`, `event_num` | 起動時の引数 |
| `sci` | SCIモードか |
| `boards` | `[{"id":..., "ip":...}]` |
| `file_started_at` | このファイルのDAQ enable を上げた時刻 [s] |

`run_period` が持つ `valid` カウンタと、起動引数を `run_file` まで渡して `publish_run_state` に与える。

### 5.2 進捗ファイル (`run/mada_progress.json`)
`ProgressMonitor.poll()` の結果を約1 Hz(0.2 s周期のポーリングのうち5回に1回)でアトミックに書き出す。

```json
{ "pid": 12345, "period_dir": "/.../per0003", "file_id": 17, "time": 1794455867.0,
  "event_num": 1000, "counts": { "GBKB-34": 420 }, "lagging": ["GBKB-35"] }
```

- `lagging` は `check_lag()` の `self.lagging` のキー。
- ファイルの取得が終わるたびに(リーダ停止の直後)削除する。DAQ終了時の `clear_run_state()` でも削除する。
  ファイルの間は進捗ファイルが無く、クライアントは `boards` が空の応答を返す(`stale` にはしない)。
- 書き込みに失敗してもDAQは止めない(警告ログのみ)。

### 5.3 終了記録 (`run/mada_last_exit.json`)
`mada.py` の `main()` で、終了理由を書く。起動時には前回の記録を消す。

| 経路 | reason | message |
|---|---|---|
| `KeyboardInterrupt`(Ctrl+C、SIGTERM) | `stopped` | なし |
| `MadaError` | `error` | 例外メッセージ |
| その他の例外 | `error` | 例外の型とメッセージ(現状は未捕捉でトレースバックのみ) |

内容は API契約 4.8 のとおり(`reason`、 `message`、 `time`、 `run`、 `period`)。SIGKILL等では書かれない(その場合は `crashed`)。

### 5.4 soft 停止の要求 (`run/mada_stop_request.json`)
クライアントが書く `{ "pid": 12345, "mode": "soft", "time": 1794455867.0 }`。 `mada.py` は `run_period` の各ファイルが終わった
直後に読み、自分のPIDの要求があれば `KeyboardInterrupt` と同じ終了処理に進む(新しいファイルは始めない)。起動時に前回の要求を消す。
`/status` の `daq.stop_mode` は、クライアントが記録した停止の種類(`mada_client.json` の `stop`)から返す。

### 5.5 変更しないもの
`mada_file_cycle.py` の1ファイル内の取得手順、ボードへのコマンド、 `.mada`/`.info` の形式、 `mada_stop_daq.py`、
スキャン・較正のプログラムには手を入れない(5.4 の確認は `run_period` のファイル間に1箇所足すだけ)。

## 6. 実装の順序

1. MADA本体の変更(5.1-5.3)と、手動起動での確認。
2. クライアントの読み取り系(`status`、 `progress`、 `files`、 `warnings`、 `log`、 `config`)とシミュレータ。
3. 開始・停止と排他。実機で `mada.py -d` の起動、停止、起動失敗、二重起動を確認。
4. 認証、サービス化、操作ログ。
5. 試験: 模擬の `MADAHOME` でAPI全体を自動試験(pytest)。実機では、停止中の `stopping`、デーモン化後の失敗、
   クライアントの再起動後の状態復元を確認する。
